Эволюция сетевого взаимодействия в Python

От системного вызова socket() до постоянного двустороннего канала: как один и тот же TCP-поток байтов постепенно оброс протоколами, моделями обработки запросов и асинхронностью.

Цель: понять, как Python работает с сетью на низком и высоком уровнях. Ниже — краткий отчёт по четырём вопросам исследования, каждый со схемой.

1

Модуль socket: обмен данными между клиентом и сервером

Как работает модуль socket в Python? Концептуальная схема обмена данными.

Модуль socket — это тонкая обёртка над системными вызовами BSD-сокетов ядра ОС. Python почти ничего не добавляет от себя: он передаёт вызовы bind, listen, accept, send, recv в ядро и возвращает результат. Сокет — это дескриптор, через который процесс читает и пишет байты; адресуется он парой (IP, порт).

Чаще всего используют семейство AF_INET (IPv4) и тип SOCK_STREAM (TCP) — надёжный упорядоченный поток байтов. Альтернатива — SOCK_DGRAM (UDP): отдельные датаграммы без гарантии доставки и порядка.

# сервер
import socket

srv = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
srv.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
srv.bind(("0.0.0.0", 8080))
srv.listen(128)

while True:
    conn, addr = srv.accept()      # блокируется до подключения
    with conn:
        data = conn.recv(1024)     # до 1024 байт, может вернуть меньше
        conn.sendall(b"PONG\n")

# клиент
cli = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
cli.connect(("127.0.0.1", 8080))
cli.sendall(b"PING\n")
print(cli.recv(1024))
cli.close()

Главное следствие потоковой природы TCP: границ сообщений не существует. recv(1024) может вернуть половину сообщения или сразу два, поэтому любой прикладной протокол сам определяет границы — через длину в заголовке, разделитель \n или фиксированный размер. Именно из этой задачи и вырастают HTTP и WebSocket.

2

Блокирующие и неблокирующие сокеты

В чём разница между блокирующими и неблокирующими сокетами?

По умолчанию сокет блокирующий: accept(), recv() и send() не возвращают управление, пока операция не станет возможной. Поток при этом ничего не делает — он снят с процессора и ждёт события от ядра. Код получается линейным и понятным, но один поток обслуживает ровно одно соединение.

После sock.setblocking(False) те же вызовы возвращаются мгновенно: если данных нет, поднимается BlockingIOError вместо ожидания. Опрашивать сокеты в цикле бессмысленно — процессор сгорит впустую, поэтому неблокирующие сокеты всегда идут в паре с механизмом уведомления о готовности: select, poll, epoll (Linux), kqueue (BSD/macOS). В Python это модуль selectors, а поверх него — asyncio.

import selectors, socket

sel = selectors.DefaultSelector()   # epoll на Linux
srv.setblocking(False)
sel.register(srv, selectors.EVENT_READ)

while True:
    for key, _ in sel.select():     # единственная точка ожидания
        if key.fileobj is srv:
            conn, _ = srv.accept()
            conn.setblocking(False)
            sel.register(conn, selectors.EVENT_READ)
        else:
            data = key.fileobj.recv(1024)   # данные точно есть
            ...

HTTP-сервер и модели обработки запросов

Что такое HTTP-сервер и как он обрабатывает входящие запросы?

HTTP-сервер — это программа поверх обычного TCP-сокета, которая умеет разбирать текстовый протокол HTTP. Она принимает соединение, читает стартовую строку (GET /page HTTP/1.1), заголовки до пустой строки, при необходимости тело по Content-Length, вызывает прикладной код и отправляет обратно статус, заголовки и тело. Модель — «запрос-ответ»: инициатива всегда у клиента, сервер сам ничего не присылает.

HTTP/1.1 200 OK          # всё это — просто байты в TCP-сокете
Content-Type: text/plain; charset=utf-8
Content-Length: 5

hello

Различия между серверами начинаются там, где запросов становится много. Обработка одного запроса — это в основном ожидание: чтение из сети, поход в базу, чтение файла. Три классических способа распорядиться этим ожиданием:

В стандартной библиотеке есть http.server — учебный однопоточный сервер, для продакшена он не предназначен. Реальная схема: Nginx принимает соединения и отдаёт статику, а динамику передаёт серверу приложений (Gunicorn, Uvicorn), который уже общается с кодом на Python через WSGI или ASGI.

4

WebSocket: постоянный двусторонний канал

Что такое WebSocket и чем его реализация в Python отличается от классического HTTP?

WebSocket (RFC 6455) решает проблему, которую HTTP не решает по своей природе: сервер не может заговорить первым. Соединение начинается как обычный HTTP-запрос с заголовком Upgrade: websocket, сервер отвечает статусом 101 Switching Protocols — и то же самое TCP-соединение дальше живёт по другим правилам: кадры (frames) летят в обе стороны, пока одна из сторон не закроет канал.

Чем отличается реализация в Python

Классический синхронный стек Python устроен под HTTP: WSGI-приложение — это функция, которая один раз получает запрос и один раз возвращает ответ. Долгоживущего соединения в этой модели просто нет, поэтому WebSocket на WSGI не реализуется. Отсюда и появился ASGI — асинхронный интерфейс с событиями receive / send и типом соединения websocket.

  • Соединение вместо запроса. Обработчик живёт всё время сессии и хранит состояние: кто подключён, в какой комнате, что уже отправлено.
  • Только асинхронный стек. websockets, aiohttp, FastAPI / Starlette, Django Channels; запускается через Uvicorn, Daphne или Hypercorn — не через Gunicorn sync.
  • Своя маршрутизация. В HTTP роутинг по URL и методу, в WebSocket URL один, а «команды» приложение раскладывает само — обычно JSON внутри кадра.
  • Масштабирование сложнее. Соединения привязаны к процессу, поэтому для рассылки между воркерами нужен внешний слой (Redis pub/sub в Channels).
  • Нет кеширования и идемпотентности. Всё, что в HTTP давал протокол, — коды статусов, повторные запросы, кеш — здесь реализует само приложение.
import asyncio, websockets

async def handler(ws):                # живёт, пока клиент подключён
    async for message in ws:          # поток кадров, а не один запрос
        await ws.send(f"эхо: {message}")

async def main():
    async with websockets.serve(handler, "0.0.0.0", 8765):
        await asyncio.Future()

asyncio.run(main())

Практическое правило: если данные нужны по запросу пользователя — берём HTTP; если обновления приходят от сервера чаще, чем пользователь готов нажимать «обновить», — WebSocket. Когда поток нужен только в одну сторону (лента событий, прогресс задачи), достаточно более простого Server-Sent Events поверх обычного HTTP.

Вывод. Вся эволюция — это надстройки над одним и тем же потоком байтов в TCP-сокете. Сокеты дают транспорт, но не дают границ сообщений; HTTP добавляет границы и семантику запроса-ответа; модели процессов, потоков и цикла событий решают, как обслуживать много таких обменов одновременно; WebSocket снимает последнее ограничение — одностороннюю инициативу — и требует за это асинхронного стека и ручного управления состоянием.
